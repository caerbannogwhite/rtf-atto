# rtf-atto

rtf-atto is an RTF reader in C++17.
It targets clinical tables made by SAS and also reads general RTF.
A writer and a TypeScript renderer will come later.

## Build and test

With the default generator (Visual Studio on Windows, Make on Linux and macOS):

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
    cmake --build build --config Release -j 8
    ctest --test-dir build -C Release --output-on-failure

With Ninja:

    cmake -S . -B build-gcc -G Ninja -DCMAKE_BUILD_TYPE=Release
    cmake --build build-gcc
    ctest --test-dir build-gcc --output-on-failure

CMake options:

- `RTF_BUILD_TESTS` builds the tests. It is on when rtf-atto is the top-level project.
- `RTF_BUILD_TOOLS` builds the `rtf2json` command. It is on by default.
- `RTF_SANITIZE` builds with AddressSanitizer and UBSan. It does not apply to MSVC.
- `RTF_FUZZ` builds the libFuzzer target `fuzz_parse`. It needs Clang.

The tests need Python 3 for the text comparison against `test/tools/rtf_text.py`.
The environment variable `RTF_MUTATIONS` sets the number of mutations in the
mutation test. `RTF_LARGE_SECONDS` sets the time budget of the large-input test.

## Sanitizers and fuzzing

On Linux and macOS, `-DRTF_SANITIZE=ON` builds everything with
AddressSanitizer and UBSan under GCC or Clang. CI runs that build on Ubuntu.

On Windows the MSVC compiler ignores `RTF_SANITIZE`. Use the Clang that
Visual Studio installs (the component "C++ Clang tools for Windows"). CMake
needs the compiler and a resource compiler from the same directory:

    CLANG="C:/Program Files/Microsoft Visual Studio/2022/Community/VC/Tools/Llvm/x64/bin"
    cmake -S . -B build-asan -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DRTF_SANITIZE=ON -DCMAKE_CXX_COMPILER="$CLANG/clang++.exe" -DCMAKE_RC_COMPILER="$CLANG/llvm-rc.exe"
    cmake --build build-asan
    RTF_MUTATIONS=2000 ctest --test-dir build-asan --output-on-failure

In that build the mutation test does not enforce its memory cap, because
AddressSanitizer on Windows provides `operator new` itself. Its other checks
run.

The fuzzer needs Clang on every platform. Build it alone and seed it with the
fixtures. Crash inputs land in the current directory as `crash-*` files,
which git ignores:

    cmake -S . -B build-fuzz -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DRTF_FUZZ=ON -DRTF_BUILD_TESTS=OFF -DRTF_BUILD_TOOLS=OFF -DCMAKE_CXX_COMPILER="$CLANG/clang++.exe" -DCMAKE_RC_COMPILER="$CLANG/llvm-rc.exe"
    cmake --build build-fuzz
    mkdir -p build-fuzz/corpus
    build-fuzz/fuzz_parse -max_total_time=600 -max_len=20000 -timeout=5 build-fuzz/corpus test/fixtures

On Linux and macOS leave out the two compiler options when `clang++` is the
default compiler, or pass `-DCMAKE_CXX_COMPILER=clang++`.

## The command

    rtf2json [--json|--text|--tables|--summary] [--version] <file>

- `--json` writes the document model as JSON. This is the default.
- `--text` writes the plain text of the document.
- `--tables` writes the logical tables as JSON.
- `--summary` writes the file name, the number of sections and tables,
  the column names of each table and the warning codes.
- `--version` prints the version.

Exit codes: 0 for success, 1 when the file is not RTF, 2 for a usage error
or a file that cannot be read.

## npm package

The package `rtf-atto` on npm is the reader compiled to WebAssembly.
`js/` holds the TypeScript wrapper, the model types and the node tests.
`wasm/` holds the C ABI and the Emscripten build.
You need Emscripten (with `emcmake` on the PATH) and CMake.
On Windows you also need Ninja on the PATH.

    cd js
    npm install
    npm run build
    npm test

See `js/README.md` for the API, the model and the error codes.

The package also renders a document to HTML. `npm run demo` in `js` starts
a page that shows the fixtures and local files in the browser.

## Fixtures and goldens

The files in `test/fixtures` are the test inputs. There are 19.
Ten are generated by `test/tools/make_fixtures.py`. Five are written by
hand. Four come from the owner's own synthetic
files: three saved by Word (`msword_*.rtf`) and one made by SAS
(`sas_disposition.rtf`). Each fixture has a golden `.json` file and a
`.tables.json` file.

To regenerate the goldens after a deliberate change:

    python test/tools/regen_goldens.py build/Release/rtf2json.exe test/fixtures

Review the diff of the goldens like code. A changed golden means the
output of the reader changed.

The npm package has 17 HTML goldens in `js/test/goldens`, one for each
fixture that parses. They are the output of the HTML renderer. To
regenerate them after a deliberate change to the renderer, run
`npm run regen:html` in `js`, after `npm run build`.

## Local samples

The owner keeps private SAS files outside the repository.
This script checks them:

    RTF_SAMPLES_DIR=<dir> [RTF2JSON=<path>] [PYTHON=<command>] bash test/local/samples.sh

- `RTF_SAMPLES_DIR` is the directory with the `.rtf` files. It is required.
- `RTF2JSON` is the tool. By default the script looks in `build` and `build-gcc`.
- `PYTHON` is the Python command. By default it is `python3`, else `python`.

On the first run the script writes `expected.txt` into the samples directory.
Review it against what Word shows. On later runs it compares each file with
its block and reports `new` for files without one. It also compares the text
of every file with `rtf_text.py`. `expected.txt` stays next to the samples
and is never committed.

## Releasing

The version lives in `js/package.json`, in `include/rtf/version.hpp` and in the
`rtf_version()` string, and a test pins the three to the same text. A release
is a plain tag `vX.Y.Z` on `main`. The codename goes in the title of the
GitHub release, not in the version, because npm reads a suffix such as
`-mortician` as a pre-release that `^` ranges skip. The first version of the
package is published by hand from `js` with `npm publish`. After that the
`publish` workflow publishes every tag with provenance through npm's trusted
publishing. A tag whose version is already on npm publishes nothing.
